# Keyboard bug hunt — 2026-10-31

## Why this hunt exists

The owner asked for a hunt over the whole repository — "bugs, flaws, issues, performance issues,
etc" — without naming a symptom. The two previous hunts
([`BUG-AUDIT-2026-10-25.md`](BUG-AUDIT-2026-10-25.md),
[`BUG-HUNT-2026-10-30.md`](BUG-HUNT-2026-10-30.md)) worked from the CI harness and then from the
gesture/clock/preference layer. This one went to the places those two did not:

- **split mode**, whose geometry is shared by drawing, hit-testing, the a11y tree and the swipe
  model;
- the **accessibility geometry** — the one consumer of the key rectangles that had its own copy of
  the layout walk;
- the **publication** of background-built data to main-thread readers (emoji index);
- **allocations** on per-keystroke and per-word paths;
- the **recent phase-3 wrappers** (floating, split) whose arithmetic is checkable without a device;
- and the **test suite as infrastructure** rather than as coverage.

Rules, unchanged from last time: a finding needs an executed path and a stated harm (otherwise it is
labelled "latent"), and owner decisions are off-limits — default layout, the Gboard-glass theme,
the migration markers, the seven-button toolbar, the clipboard-keeps-everything policy and the
fixes documented in the two earlier reports are constraints, not candidates.

## The biggest result: the tests had never been run

`AGENTS.md` explains why CI runs `assembleDebug` and never `test`: upstream's release-record drift
tests assert on files this fork does not vendor. What that note did not say is that **449 test files
and 4,689 `@Test` methods have therefore never executed in this repository** — including every
ratchet test the earlier hunts added as their own proof.

This pass made the portable subset run **on every build** (`build-apk.yml`), advisory
(`continue-on-error`) and reported as annotations. Its first run found:

1. a **live defect in split mode** (fix #1 below) that had a red test written against it all along;
2. a wrong expectation in the test added by this hunt (fixed);
3. six failures in two test classes that had quietly rotted (fix #11).

That is the argument for the change: a red test nobody runs is worse than no test, because the
report says the invariant is protected. The subset is now **448 tests in 40 classes, green**.

## Fixed in this pass

| # | Severity | Defect | Fix |
|---|---|---|---|
| 1 | **High** (split mode) | `KeyboardGeometry.rowSpans` inserted the split gap **once per right-half key** instead of once per row: `SplitConfig.isRightHalf(totalUnits, leftUnits)` is true for every key from the midpoint onward and sat inside the per-key loop, so a five-key right half was pushed right by five gaps. At the shipped 10 % default the right half hung more than a third of the keyboard past the content edge and the `splitScale` compensation shrank it into empty space. Drawing, hit-testing, the a11y tree and the swipe model all read `rowSpans`, so they agreed with each other and disagreed with the intended geometry — no mismatch to blame. Caught by `SplitKeyboardGeometryTest`: expected 1000, got 1400. | Latch: open the gap at the first key whose left edge reaches the midpoint, then never again (`KeyboardGeometry.kt:229-262`). Split off is unchanged; every consumer is fixed at once. |
| 2 | **Medium** (a11y, split) | `computeAccessibilityKeyRects` (`KeyboardGeometry.kt:280-325`) had its own horizontal walk — `x + key.shift * keyWidth`, advancing by `key.width * keyWidth` — so it applied neither the gap nor the scale. With split on, every TalkBack node on the right half named a region up to a gap away from the key a finger actually hits. The invariant was pinned by `accessibilityRectsMatchFilteredKeyAtAcrossEveryPixel`, but its fixture had `splitGap = 0`, so it could never fail. | Walks `rowSpans`, and gives each node the previous cell's right edge as its left edge — the rule `keyAt` uses, where the space before a key (including the gap) belongs to the key on its right. New test `accessibilityRectsFollowSplitGapAndScale` re-runs the every-pixel invariant with gap 210 px / scale 0.79 and pins the gap arithmetic *and* the ownership rule. |
| 3 | **Low–Medium** (thread safety) | `EmojiKeywordIndex` published its trie with plain `var`s: built on `Dispatchers.IO`, read from the emoji search `TextWatcher` on the main thread, no happens-before edge. | `rootNode` / `isLoaded` are `@Volatile` (`:37,42`); the ordering requirement is documented on the field. |
| 4 | **Low** (perf, per keystroke) | `PredictionContextTracker.normalizeForPrediction` compiled `Regex("\\p{Mn}")` on every call — twice per `synchronizeWithCursor`, plus once per committed word. | Hoisted to `COMBINING_MARKS` (`:85`), used at `:863`. |
| 5 | **Low** (perf, dictionary load) | `MainDictionarySource`'s JSON fallback compiled `Regex("^[\\p{L}'-]+$")` **inside the per-word loop**. | Hoisted to `VALID_WORD` (`DictionaryDataSource.kt:357`), used at `:139`. |
| 6 | **Low** (latent, preview) | `Keyboard2View.getRealKeyPositions()` had its own shift-only accumulation, so the theme editor's sample trail ignored split mode; also corrected the draw-cache comment claiming `keyAt` never calls `rowSpans`. | Walks `rowSpans` with `geometryParams()` (`:1447-1487`). |
| 7 | **Medium** (floating mode) | The floating y cap was a fraction of the **screen** (`MAX_Y_FRACTION = 0.9f`), not of the space the keyboard leaves. On a 2400 px screen with a 38 % keyboard, `y = 0.9 * 2400 = 2160` puts the bottom edge at 3070 px: the whole bottom row (space, period, enter) is below the display. The fraction persists, so the keyboard comes back off-screen next time it floats. | `FloatingConfig.maxYFraction(screenHeight, windowHeightPx)` caps by the measured window height; `yPixels`/`window` take that height (default 0 keeps the old cap before the first layout pass); the drag handler and the persist path clamp with the same helper, so a drag cannot bank a value layout would reject; a layout listener re-resolves the geometry when the keyboard's height changes. Four new `FloatingConfigTest` cases. |
| 8 | **Medium** (perf, default path) | `Defaults.SWIPE_TRAIL_EFFECT = "sparkle"` — the shipped look — drew **three `BlurMaskFilter`ed circles per path sample per frame**, each with its own `sin` and half a dozen float multiplies, mutating `paint.alpha` per particle. A one-second swipe is a few hundred samples, i.e. ~600–1,000 blurred `drawCircle` calls per frame at 60 Hz. The `rainbow` branch also allocated a `FloatArray` per frame. | Past 360 particles the sampling stride thins the trail **uniformly** — density along the path is what the eye reads, so a normal swipe is pixel-identical — which bounds frame cost instead of letting it grow with gesture length. `rainbow` writes into a reused scratch array. |
| 9 | **Medium** (startup) | `ClipboardHistoryService`'s constructor ran TTL housekeeping on the IME main thread before the keyboard could draw: open the database, scan and delete expired rows, then `File.delete()` each expired clip's media. With the default unlimited history that is unbounded work on the startup path. | The job is now the first half of the existing IO coroutine, ahead of the orphan sweep, in a named `reconcileExpiredEntries()`. Reads filter on `expiry_timestamp` themselves, so the only visible difference is that a row the cleanup is about to delete can be listed for a few milliseconds. |
| 10 | **Low** (three small items) | (a) `CleverKeysService.get_imm()` derefs `_subtypeManager!!` and has **zero callers** — dead code with an NPE waiting for the degenerate no-config startup path `refreshSubtypeImm` explicitly supports. (b) `EmojiKeywordIndex.search` logged a **warning** on every keystroke typed before the index finished loading — an expected state the UI already gates on. (c) `Autocapitalisation.event_sent` set `shouldEnableShift = false` and `shouldUpdateCapsMode = false` for a meta-modified key and then **returned without publishing**, so the decision applied one key late and the visual shift state lagged. | (a) deleted. (b) verbose-only `Log.d` under `BuildConfig.ENABLE_VERBOSE_LOGGING`. (c) publishes via `callback(true)` — shift off now, and the caps mode is deliberately not re-consulted (a modified key is not a sentence boundary). New test pins both halves. |
| 11 | **Medium** (test rot) | Five of the six failures in the wider filter were one shape: the code reads the **effective** gates (`Config.autocapEffective`, `Config.clipboardHistoryEffective` — setting AND incognito) while the tests stubbed the raw `autocapitalisation` / `clipboard_history_enabled` fields on a relaxed mock. A relaxed mock answers `false` for a computed Boolean property, so `AutocapitalisationTest` ran with auto-cap *disabled* (3 failures) and `ClipboardCatchUpTest`'s catch-up returned before reading anything — meaning its "no re-read on every show" assertions had been passing without the catch-up ever running. | Both test classes stub the effective property, with a comment saying why; the disabled-case tests stub it `false` explicitly. 448 tests now pass, and the catch-up assertions are meaningful again. |

## Reported, not fixed

### R1 — resolved: the 16 skip, and the whole suite runs nightly

**What was wrong.** Sixteen classes assert on upstream artefacts this fork does not vendor
(`docs/RELEASE_RECORD.md`, `RELEASE_NOTES.md`, `fastlane/`, `metadata/fdroid/`,
`docs/i18n/glossary.json`, `.github/scripts/emulator-ci.sh`, `scripts/dictionaries/langpack-*.zip`).
They FAILED, so "run all the tests" could never be green, and CI ran a hand-picked `--tests`
subset instead. A filter hides whatever it does not name: `SettingsRangeDriftTest` had therefore
never executed, and the first time it did it found a real divergence (`sound_volume`'s 0..100
bound restated in three places, one of them ignored by the keyboard).

**What changed.**

- `UpstreamArtefacts` wraps JUnit's `Assume`: a missing file SKIPS the class, with the missing
  path in the message — "not checkable in this checkout" is a different claim from "the invariant
  holds", and a skipped test is not a green one. Sixteen classes use it (six release-bookkeeping,
  ten language-pack), plus one test inside `LanguagePackImportTest` whose other 50 cases are
  synthetic and still run.
- Fixtures loaded in constructors had to become `by lazy`: the constructor runs BEFORE `@Before`,
  so a guard could never fire and the class failed with "language-pack zip not found" instead of
  skipping.
- `.github/workflows/full-test-suite.yml` runs the **whole** suite nightly (03:17 UTC), on demand,
  and on any push that changes the file — 180-minute budget, 120-minute timeout avoided by
  measurement, failing-class and failing-name inventory in the annotations and the job summary.
  `build-apk.yml` keeps the cheap subset for per-push signal. Net effect: nothing can hide
  indefinitely, without a 20-minute tax on every push.

**What the first whole-suite run found** (run 41221339688: **4,673 tests, 217 failed, 53 classes** —
none of this had ever been visible before):

| cause | classes | state |
|---|---|---|
| Upstream artefacts not vendored | 16 | **skip** now (above) |
| `OutOfMemoryError: Java heap space` on the default 512 MB test heap — the geometric-engine harnesses decode sample grids against the 98,140-word English lexicon: `CandidatePrunerTest`, `GeoBenchmarkTest`, `GeoAccuracy{QwertyEn,DvorakEn,WeirdLayout}Test`, `GeoConfusablesTest`, `GeoOqSweepTest`, `GeoAblationTest`, `GeoDoubleLetterTest`, `CtcVsGeoLocalCorpusTest`, `UserSwipePriorityReplayTest` | ~11 confirmed, more among the replay harnesses | **backlog** |
| Real assertion failures, never seen before | ~20 | **backlog** |

**The 3 GB experiment, stated plainly.** Giving the test JVM 3 GB cleared the OOM cluster's
cause, and the run then passed 70 minutes without completing: those classes trade a fast OOM for
minutes of GC each. That is a budget problem, not a correctness one, and a global heap flag that
makes the whole suite unusable is not a fix — it is reverted, and the classes are recorded here.

**The backlog, in the order it is worth attacking** (each needs the failing cases re-read against
the code, not a blanket "skip"):

1. `LearningFunnelBookkeepingTest` 25/40, `LearningWiringDriftTest` 3/18, `NextWordStaticTierTest`
   2/13 — the on-device-learning wiring. Largest cluster, and the one most likely to contain a
   real defect rather than a stale expectation.
2. `SwipeCorrectionOfferTest` 22/34, `SwipeAutocapCommitTest` 6/6, `TypedBarHighlightHandlerTest`
   4/9 — the swipe/autocap commit path.
3. `PrivacyManagerTest` 21/44 — retention cut-off arithmetic (expected ≈ now − retention, got a
   value ~90 days later).
4. `WindowLayoutUtilsTest` 9/22, `CommandCatalogLocalizationTest` 3/5 (294 missing catalog strings
   across locales), `KeyFillAlphaTest` 3/4, `StyleLayoutsTest` 2/13, `CornerLabelPolicyTest` 1/6,
   `DefaultsSingleDefinitionDriftTest` 1/5, `ConfigSnapshotRatchetTest` 2/10,
   `SettingsSurfaceDriftTest` 1/6, `PointersShortSwipeCustomOverrideTest` 1/11,
   `PointersSliderSpeedTest` 1/10, `TestKeyboardSectionTest` 1/4, `TestRunnerListDriftTest` 1/2.
   Some of these are drift tests whose pinned source text moved during this week's fixes; that has

### R2 — all five carry-overs fixed (2026-10-31, follow-up pass)

| # | What was wrong | What changed |
|---|---|---|
| **N1** | `swipe_dist` had no `SettingsRanges` entry, no read clamp and no import range. `"0"` makes the threshold zero — every touch is a swipe, so a tap can never type its own key; `"9999"` puts the threshold far past anything the screen can produce. | `SettingsRanges.SWIPE_DIST = 5f..30f` — exactly the slider's range. The Config read site reads through `Config.clampedFloatPref()` (new, unit-tested), the import validator range-checks it, and `SettingsPersistence` clamps on load so the slider cannot display a number the keyboard ignores. The slider itself now uses the shared constant instead of a second copy of `5f..30f`. |
| **N2** | `ConfigurationManager.onSharedPreferenceChanged` rebuilt the whole `Config` and fanned out to every listener once per write, on the writer's (usually main) thread. A settings slider writes once per increment, so one drag was ~60 full refreshes. | Bursts are coalesced: the **first** write of a burst is applied synchronously exactly as before (a lone switch tap, theme re-inflation included), writes that follow within 150 ms are merged into a single trailing refresh 100 ms after the writes stop. If the process has no main `Looper` (plain-JVM tests) it falls back to the old synchronous behaviour. Stated trade-off: the 2nd…Nth write of a burst becomes visible ~100 ms after the drag stops instead of instantly; nothing reads a preference back mid-drag. |
| **N4** | `slider_sensitivity` imported any `[0-9]+`, so a backup could carry `0`/`9999`; Config's clamp silently rewrote it, leaving Settings showing a value the space slider never used. | Validator range-checks `SettingsRanges.SLIDER_SENSITIVITY_PERCENT` (1..100); `SettingsPersistence` clamps both its load path and its per-key change path. |
| **N5** | `ClipboardHistoryService.addClip` called `Config.globalConfig()`, which throws a `NullPointerException` before the IME builds its Config — the OS clipboard listener registers in `onCreate`, so the first copy after a cold start was lost (and the throw landed in the listener) while `storeClip` beside it used `globalConfigOrNull()`. | `addClip` uses `globalConfigOrNull()`: only an explicit "off" rejects a clip; with no Config yet there is no preference to consult, so the clip is kept. |
| **N6** | Reported as "383 unguarded `Log.d`". **That number was wrong** — see below. | The three per-update `SuggestionBar` calls are now gated, and `VerboseLogRatchetTest` caps the repo-wide count so it cannot grow. |

**N6, measured properly.** The 383 figure counted a call as guarded only when the gate sat on the
same line. This codebase writes the gate as a wrapping `if`, sometimes with several comment lines in
between, so the real number — with the gate taken to be the **enclosing block** — was **246**, and
the per-keystroke paths (`Pointers`, `SuggestionHandler`, `Autocapitalisation`,
`WordPredictor.predictInternal`) were already gated by the earlier P1/P2 work. What is left is 246
calls in cold or one-shot paths (dictionary load, backup/restore, ONNX model loading, theme preview)
where the interpolated string costs nothing because the code runs once. A mass rewrite of those
would have been churn with no measured benefit and real compile risk, so the fix is: gate the three
`SuggestionBar` calls that really do run per keystroke, and pin the rest with a ratchet.

## CI storage: the quota is still blown, and it predates this work

Measured today through the API: **81 artifacts, 3,896 MB**, none expired, all created 2026-10-21..23.

| kind | count | size |
|---|---|---|
| `keyboard-debug-*` (three APKs bundled per dispatch) | 41 | **3,834 MB** |
| `smoke-run-*` (emulator evidence) | 38 | 63 MB |
| `build-reports-*` | 2 | ~0 MB |

A private repo's Actions storage quota is 500 MB, so this is 7.8× over — and it is the *same*
backlog [`docs/CI-STORAGE.md`](CI-STORAGE.md) already measured on 2026-10-25. Nothing was ever
cleared, so every optional upload since has failed with
`Failed to CreateArtifact: Artifact storage quota has been hit`, silently, because those steps are
`continue-on-error`.

**Clearing it needs the owner**, because deletion requires `actions: write` and the Arena token does
not have it (every attempt returns `403 Resource not accessible by integration`):

```bash
gh api "repos/kb019063-hue/keyboard-/actions/artifacts?per_page=100" --paginate \
  --jq '.artifacts[] | select(.name | startswith("keyboard-debug-")) | .id' \
| while read -r id; do
    gh api -X DELETE "repos/kb019063-hue/keyboard-/actions/artifacts/$id"
  done
```

or, without a CLI token: **Actions tab → the offending run → delete the run** (that removes its
artifacts). Deleting them cannot lose an APK — every one of those 41 is already in the rolling
`dev-builds` release, which is the delivery path and does not count against this quota. Usage
recalculates on a 6–12 hour delay, so the quota frees itself gradually rather than instantly.

What this pass changed so it cannot re-accumulate: the dispatch-only APK artifact's
`retention-days` drops from 3 to **1**, and the unit-test summary is emitted as **annotations**
rather than an artifact — so a failing run stays readable even while the quota is full.

## Checked and found sound (do not re-raise)

- **`BackupCrypto` / `Pbkdf2Sha256`**: AES-256-GCM with a fresh salt+nonce per container, header
  bound as AAD, iteration cap enforced *before* key derivation, streaming encrypt/decrypt with
  explicit `update`/`doFinal` (no `CipherInputStream`), key bytes zeroed in `finally`. The
  hand-rolled PBKDF2 is correct (one `Mac` keyed once, `U1..Uc` XOR per block) and covers the API
  24/25 gap where `PBKDF2WithHmacSHA256` is unavailable.
- **Clipboard SQLite paths**: every `rawQuery` traced closes its cursor (`.use { }`), and the one
  hand-opened transaction (`updateEntryContentInTable`) has `setTransactionSuccessful` on the
  success path plus `if (db.inTransaction()) db.endTransaction()` in `finally`.
- **`Pointers` deferred-down bookkeeping**: the tap-vs-gesture decision re-checks
  `FLAG_P_DEFERRED_DOWN` per branch, cancels the long-press before the tap commit, and the
  backspace/nav-subkey paths clear the flag before falling through to classification.
- **`SuggestionBar` view pool**: click/long-press closures capture the **pool slot** index and the
  pool only reorders in slot order, so a recycled view cannot dispatch the previous suggestion's
  word; the temporary-message path suppresses suggestion writes while it is up.
- **`KeyboardData` parsing**: `load` and `load_string` both catch and fall back, and
  `add_key_to_pos` / `add_key_to_preferred_pos` bound every index before indexing.
- **`SubkeyPopoverGeometry.gridCentre`**: the `viewSize <= 2 * half` guard runs before
  `coerceIn(half, viewSize - half)`, so the reversed-range exception is unreachable; `slotAt`
  returns `null` for non-positive cell sizes.

## Test coverage added

- `KeyboardGeometryTest.accessibilityRectsFollowSplitGapAndScale` — the every-pixel "TalkBack rect
  resolves to `keyAt`'s key" invariant with split on, plus the gap-position assertions.
- `FloatingConfigTest` — four cases: the height-aware cap, the unmeasured-window fallback, "taller
  than the screen clamps to 0", and that the drag clamp and the layout clamp are the same helper.
- `AutocapitalisationTest` — "a meta-modified key publishes the cleared shift state and does not
  re-consult the caps mode", plus the effective-gate stubs that make the existing 13 cases real.
- `ClipboardCatchUpTest` — effective-gate stubs that restore six assertions which had been passing
  or failing without the catch-up ever running.

### Added by the R2 follow-up pass

- `SettingsRangeDriftTest` — six new cases: `swipe_dist` inside/outside/NaN/negative import
  behaviour, `slider_sensitivity` range rejection, the four consumer-site pins, and the
