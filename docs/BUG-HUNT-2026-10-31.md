# Keyboard bug hunt — 2026-10-31

## Why this hunt exists

The owner asked, again, for a hunt over the whole repository — "bugs, flaws, issues, performance
issues, etc" — without naming a symptom. The two previous hunts
([`BUG-AUDIT-2026-10-25.md`](BUG-AUDIT-2026-10-25.md),
[`BUG-HUNT-2026-10-30.md`](BUG-HUNT-2026-10-30.md)) worked from the CI harness and then from the
gesture/clock/preference layer. This one went to the places those two did not:

- the **accessibility geometry** — the one consumer of the key rectangles that had its own copy of
  the layout walk;
- **split mode**, whose geometry is shared by drawing, hit-testing, the a11y tree and the swipe
  model;
- the **publication** of background-built data to main-thread readers (emoji index);
- **per-keystroke / per-word allocations** on the prediction and dictionary paths;
- and the **test suite as infrastructure** rather than as coverage.

The rules are the same two as last time:

1. **A finding needs an executed path and a stated harm.** Anything I could not trace to a caller is
   labelled "latent" rather than dressed up as user-visible.
2. **Owner decisions are off-limits.** Default layout, the Gboard-glass theme, migration markers,
   the seven-button toolbar, the clipboard-keeps-everything policy and the fixes documented in the
   two earlier reports are constraints, not candidates.

## The biggest result: the tests had never been run, and the first run broke split mode

`AGENTS.md` explains why CI runs `assembleDebug` and never `test`: the upstream release-record drift
tests assert on files this fork does not vendor. What that note does not say is that the **449 test
files / 4,689 `@Test` methods have therefore never executed here** — including every ratchet test the
three hunts of fixes added as their own proof.

This pass added a manually-dispatched `unit_tests` input to `build-apk.yml` and ran the portable
subset (a11y, popover, gesture, prefs: 9 classes, 107 tests). It went red on two tests:

```
SplitKeyboardGeometryTest#scale plus gap fills exactly the unsplit width
    value of : getXRight() expected : 1000.0 but was : 1400.0
KeyboardGeometryTest#accessibilityRectsFollowSplitGapAndScale   (the test added in this pass)
```

The first is a **live defect in split mode**, which is the subject of fix #1 below and had been
sitting behind a red test since the mode was written. That is the whole argument for the
recommendation in F4: a red test nobody runs is worse than no test, because the report says the
invariant is protected.

## Fixed in this pass

| # | Severity | Defect | Fix |
|---|---|---|---|
| 1 | **High** (split mode geometry) | `KeyboardGeometry.rowSpans` inserted the split gap **once per right-half key** instead of once per row. The condition `SplitConfig.isRightHalf(totalUnits, leftUnits)` is true for *every* key from the row midpoint onward, and it sat inside the per-key loop, so a five-key right half was pushed right by five gaps. With the shipped 10 % default that is +50 % of the content width: the right half hung more than a third of the keyboard past the edge and the `splitScale` compensation shrank it into empty space. Because drawing (`drawRowSpans`), hit-testing (`keyAt`), the a11y tree (`computeKeyRects`) and the swipe model all read `rowSpans`, they agreed with each other and disagreed with the intended geometry — which is why there was no visible mismatch to blame. Caught by `SplitKeyboardGeometryTest` expecting 1000 and getting 1400. | Latch: open the gap at the first key whose left edge reaches the midpoint, then never again (`KeyboardGeometry.kt:229-262`). With split off nothing changes (gap 0 → the latch is never armed). Only the affected keys move; every consumer is fixed at once. |
| 2 | **Medium** (accessibility, split mode) | `computeAccessibilityKeyRects` (`KeyboardGeometry.kt:280-325`) had its own horizontal walk — `physicalLeft = x + key.shift * keyWidth`, advancing by `key.width * keyWidth` — instead of `rowSpans`, so it applied neither the split gap nor the compensating scale. With split on, every TalkBack node on the right half named a region up to a gap away from the key a finger would actually hit, and its width was the unsplit width; touch exploration announced the wrong key. The invariant was already pinned by `accessibilityRectsMatchFilteredKeyAtAcrossEveryPixel`, but its fixture had `splitGap = 0`, so it could never fail. | The walk now goes through `rowSpans` and assigns each node the previous cell's right edge as its left edge — the same rule `keyAt` uses, where the space *before* a key (including the split gap) belongs to the key on its right. New test `KeyboardGeometryTest.accessibilityRectsFollowSplitGapAndScale` re-runs the every-pixel invariant with a 210 px gap / 0.79 scale and pins both the gap arithmetic and the ownership rule. |
| 3 | **Low–Medium** (thread safety) | `EmojiKeywordIndex` published its trie with plain `var`s: `prewarm()` builds the `TrieNode` graph on `Dispatchers.IO`, `Emoji.search()` reads `rootNode`/`isLoaded` from the emoji search `TextWatcher` on the main thread. No happens-before edge, so a search could miss a fully built index, or observe a partially published graph (a JMM data race). Symptom: "emoji search finds nothing until I type another letter". | `rootNode` and `isLoaded` are `@Volatile` (`EmojiKeywordIndex.kt:37,42`), with the ordering requirement (build fully, then publish) documented at the field. |
| 4 | **Low** (perf, per keystroke) | `PredictionContextTracker.normalizeForPrediction` compiled `Regex("\\p{Mn}")` on every call — twice per `synchronizeWithCursor`, plus once per committed word. | Hoisted to `COMBINING_MARKS` in the companion (`:85`), used at `:863`. Same pattern, same NFD order. |
| 5 | **Low** (perf, dictionary load) | `MainDictionarySource`'s JSON fallback compiled `Regex("^[\\p{L}'-]+$")` **inside the per-word loop**, i.e. once per word of a tens-of-thousands-entry lexicon, on the path taken by languages with no packaged `.bin`. | Hoisted to `VALID_WORD` in the companion (`DictionaryDataSource.kt:357`), used at `:139`. |
| 6 | **Low** (latent, preview only) | `Keyboard2View.getRealKeyPositions()` (`:1447`) had its own shift-only accumulation, so with split on the theme editor's sample trail was drawn against unsplit coordinates. Also corrected the draw-cache comment that still claimed `keyAt` never calls `rowSpans` (it has since split support landed). | Now walks `rowSpans` with `geometryParams()`, the same parameters hit-testing uses (`:1447-1487`). |

## Reported, not fixed

Evidenced and actionable, but not applied: they change timing semantics, change the owner's chosen
look, or need a finger on a device.

### F1 — floating mode can be dragged until only its grip is on screen *(Medium, UX)*

`FloatingConfig` places the window's **top edge** at `screenHeight * yFraction`
(`FloatingConfig.kt:46-47`) and caps the fraction at `MAX_Y_FRACTION = 0.9f` (`:31`). Its KDoc says
the cap exists so the keyboard "can never be dragged until only its grip shows" (`:15`), but the cap
is a fraction of the **screen**, not of the space left over by the keyboard:

- window height is the keyboard's `WRAP_CONTENT` height
  (`WindowLayoutUtils.updateSoftInputWindowLayoutParams`, `:236-238`; the floating path deliberately
  leaves it alone, `:270-271`) and the gravity is `TOP|START` with `y` as the offset
  (`WindowLayoutUtils.kt:289-297`);
- on a 2400 px screen with a 38 % keyboard (≈910 px), `y = 0.9 * 2400 = 2160` puts the bottom edge at
  3070 px — **670 px (28 %) of the keyboard, the whole bottom row including space and enter, below
  the display**;
- even the default `0.62` lands the bottom edge at ≈`1.00` of the screen before navigation-bar
  insets, so the bottom of the space bar is already marginal on some devices;
- the fraction persists (`persistFloatingPosition`), so the keyboard comes back off-screen next time
  it floats. The grip is still reachable, so it is recoverable — but only if the user works out why
  half the keyboard is missing.

**Fix sketch:** make the cap depend on the window height, not a constant:
`maxYFraction = ((screenHeight - windowHeightPx) / screenHeight).coerceIn(0f, MAX_Y_FRACTION)`.
Clamp the stored fraction against it both in `currentFloatingWindow()` and in `moveFloating()`
(clamping only at use leaves the stored value stuck above the clamp, so an upward drag does nothing
until it unwinds). Pass the hosted root's measured height. Pure arithmetic → JVM-testable; the exact
height needs one device check because it includes the suggestion strip and toolbar.

### F2 — the default swipe trail is the most expensive effect, and it runs per frame *(Medium, perf)*

`Defaults.SWIPE_TRAIL_EFFECT = "sparkle"` (`Config.kt:175`), so this is the shipped look, not an
opt-in. `drawSwipeTrail`'s sparkle branch (`Keyboard2View.kt:2024-2079`) draws **three
`BlurMaskFilter`ed circles per path point on every frame** of the swipe, each with its own `sin` and
half a dozen float multiplies, mutating `paint.alpha` per particle. The path is one point per
accepted move sample (`ImprovedSwipeGestureRecognizer.addPoint`), so a one-second word swipe is a few
hundred samples → ~600–1,000 blurred circles per frame at 60 Hz for the duration of the gesture. The
`rainbow` branch also allocates a `floatArrayOf` per frame (`:2016-2019`).

This is the same class of cost the 2026-10-25 audit removed from the toolbar and the suggestion
strip, on the one path where the user is actively dragging a finger.

**Fix sketch:** (a) stride the particle loop (every 2nd/3rd point); (b) precompute the per-index
pseudo-random offsets once per swipe — the seeds are already stable, so the values are too; (c) keep
the blur on the base trail and drop it from the particles; (d) hoist the `floatArrayOf` into a field.
(a)–(c) change the look, which is the owner's call.

### F3 — the clipboard history constructor does database cleanup and file deletes on the caller's thread *(Medium, perf/ANR)*

`ClipboardHistoryService`'s TTL block (`ClipboardHistoryService.kt:139-165`) synchronously opens the
database, scans and deletes expired rows, and then calls `File.delete()` per expired row's media
file — on the thread that constructs the service, which is the IME main thread
(`CleverKeysService.onCreate` → `on_startup`, `:1210`). Only the orphan sweep just below it is
dispatched to `Dispatchers.IO` (`:157`). With the default unlimited history and a lot of media clips
that is unbounded disk I/O before the keyboard draws for the first time.

**Fix sketch:** move the TTL block into the existing `serviceScope.launch(Dispatchers.IO)`, ordered
before `getAllReferencedMediaPaths()` so the orphan sweep sees the post-cleanup table. The database
is thread-safe; the only behavioural change is that an expired row can survive for the milliseconds
until the job runs, and `clearExpiredAndGetHistory()` already does the same work on demand.

### F4 — the unit-test suite cannot pass, and CI never runs it *(High, process)*

Everything in the "biggest result" section above is the evidence: the split-mode defect had a red
test written against it and nobody knew.

- `build-apk.yml` has no test step on `push`; 4,689 test methods have never run here.
- At least **16 test files reference paths this tree does not contain**, so `./gradlew test` cannot
  be green anyway: `docs/RELEASE_RECORD.md` (LayoutCatalogueTest, ReleaseClaimNavBarTest,
  ReleaseClaimTextActionsTest, ReleasePackagingDriftTest, ReleaseRecordDriftTest,
  SettingsSearchCoverageTest, SuggestionTapPartialReplaceTest, ReleaseClaimCommandCatalogueTest),
  `RELEASE_NOTES.md` + `fastlane/` (ReleaseMetadataDriftTest), `.github/scripts/emulator-ci.sh`
  (CuratedInstrumentationListTest), `docs/i18n/glossary.json` (TranslationGlossaryTest), and
  `scripts/dictionaries/langpack-*.zip` (the CTC/pack tests, the Hebrew autocorrect evals,
  NoticeModelAttributionDriftTest). `docs/i18n/glossary.json` is also read by
  `scripts/export_translation_review.py`, so that tooling points at a file that is not in the repo.
- Consequence: a change that breaks `KeyboardGeometryTest`, `ConfigSnapshotRatchetTest` or
  `SettingsRangeDriftTest` ships silently — and at least one did (fix #1), plus the a11y invariant
  (fix #2) was written with a fixture that could not fail.

**What this pass did about it (non-invasive half):** `build-apk.yml` now has a `workflow_dispatch`
input `unit_tests` (default **off**) that compiles the whole test source set and runs the portable
packages, reporting a per-class JUnit summary **and each failing case with its assertion message** as
annotations, because the raw logs on `results-receiver` are unreachable outside the web UI
(`docs/CI-STORAGE.md`). `continue-on-error` keeps it advisory: it can never block the APK push path.
The first such run found fix #1 within six minutes.

**What still needs the owner's decision:** run that subset on `push` too (or nightly). It costs
~1–2 minutes of runner time and one extra job; the annotation limit is respected by reporting at most
ten failing cases. The known-broken release-record classes stay out via `--tests` filters rather than
by fixing upstream drift (which is out of scope per `PROVENANCE.md`).

**CI note:** the run that hit a failure tried to upload the failure report and got
`Failed to CreateArtifact: Artifact storage quota has been hit`, so failure reports are currently
unavailable until the quota resets — another reason the annotation path, not artifacts, is the right
way to surface results here.

### F5 — small things worth a sweep, not a report each

- `CleverKeysService.get_imm()` (`:603-605`) derefs `_subtypeManager!!` and has **no callers** — dead
  code with an NPE waiting for its first use on the degenerate no-config startup path that
  `refreshSubtypeImm` explicitly supports (`:613-617`). Delete it or make it lazy.
- `EmojiKeywordIndex.search` logs `Log.w("Search called before index loaded")` on every keystroke
  typed in the emoji search box before the background load completes — an expected state, logged as
  a warning, on the search path.
- `Autocapitalisation.event_sent` returns before calling `callback` when `meta != 0` (`:62-67`): it
  sets `shouldEnableShift = false` and `shouldUpdateCapsMode = false`, then returns. Not re-arming
  shift for a Ctrl/Alt combination is deliberate; the side effect is that the decision is only
  *applied* on the next unmodified key, so after a Shift+letter event the visual shift state can lag
  by one key. One tap on a device settles it; not asserted here.

## Carried over from 2026-10-30 — still open, not re-argued

- **N1** `swipe_dist` has no `SettingsRanges` entry, no read clamp and no import range; `0` turns

- **N2** `ConfigurationManager.onSharedPreferenceChanged` refreshes the whole `Config` (and fans out

  drag in Settings is N full refreshes on the main thread.
- **N4** `slider_sensitivity` imports any `[0-9]+`, so Settings can display a value the keyboard
  clamps; `SettingsPersistence` does not clamp on load.
- **N5** `ClipboardHistoryService.addClip` still calls `Config.globalConfig()` (throws on a cold

- **N6** 383 unguarded `Log.d` / 126 `Log.i` call sites in a debug build; the interpolated messages
  are built even when the level is filtered.

## Checked and found sound (do not re-raise)

- **`BackupCrypto` / `Pbkdf2Sha256`**: AES-256-GCM with a fresh salt+nonce per container, header
  bound as AAD, iteration cap enforced *before* key derivation, streaming encrypt/decrypt with
  explicit `update`/`doFinal` (no `CipherInputStream`), key bytes zeroed in `finally`. The
  hand-rolled PBKDF2 is correct (one `Mac` keyed once, `U1..Uc` XOR accumulated per block) and
  covers the API 24/25 gap where `PBKDF2WithHmacSHA256` is unavailable.
- **Clipboard SQLite paths**: every `rawQuery` I traced closes its cursor (`.use { }`), and the one
  hand-opened transaction (`updateEntryContentInTable`) has `setTransactionSuccessful` on the success
  path plus `if (db.inTransaction()) db.endTransaction()` in `finally`.
- **`Pointers` deferred-down bookkeeping**: the tap-vs-gesture decision re-checks
  `FLAG_P_DEFERRED_DOWN` per branch, cancels the long-press before the tap commit, and the
  backspace/nav-subkey paths both clear the flag before falling through to classification.
- **`SuggestionBar` view pool**: click/long-press closures capture the **pool slot** index and the
  pool only ever reorders in slot order, so a recycled view cannot dispatch the previous
  suggestion's word; the temporary-message path suppresses suggestion writes while it is up.
- **`KeyboardData` parsing**: both `load` and `load_string` catch and fall back (a malformed custom
  layout cannot take the IME down), and `add_key_to_pos` / `add_key_to_preferred_pos` bound every
  index by `minOf(row, rows.size - 1)` / `row.keys.size - 1` before indexing.
- **`SubkeyPopoverGeometry.gridCentre`**: the `viewSize <= 2 * half` guard runs before
  `coerceIn(half, viewSize - half)`, so the reversed-range `IllegalArgumentException` is unreachable;
  `slotAt` returns `null` for non-positive cell sizes.
