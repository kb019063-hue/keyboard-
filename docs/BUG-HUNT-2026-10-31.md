# Keyboard bug hunt — 2026-10-31

## Why this hunt exists

The owner asked, again, for a hunt over the whole repository — "bugs, flaws, issues, performance
issues, etc" — without naming a symptom. The two previous hunts
([`BUG-AUDIT-2026-10-25.md`](BUG-AUDIT-2026-10-25.md),
[`BUG-HUNT-2026-10-30.md`](BUG-HUNT-2026-10-30.md)) worked from the CI harness and then from the
gesture/clock/preference layer. This one deliberately went to the places those two did not:

- the **accessibility geometry** (the one consumer of the keyboard's key rectangles that was never
  reconciled with split mode),
- the **publication** of background-built data to the main-thread readers (emoji index),
- **per-keystroke / per-word allocations** on the prediction and dictionary paths,
- the **recent phase-3 wrappers** (floating, split) whose geometry is pure arithmetic and therefore
  checkable without a device,
- and the **test suite as infrastructure** rather than as coverage.

The same two rules as the 2026-10-30 hunt apply:

1. **A finding needs an executed path and a stated harm.** Anything I could not trace to a caller is
   labelled "latent" instead of dressed up as user-visible.
2. **Owner decisions are off-limits.** Default layout, the Gboard-glass theme, migration markers,
   the seven-button toolbar and the fixes documented in the two earlier reports are constraints,
   not candidates.

Four defects are fixed here, six are reported with evidence and a fix sketch, and the parts that
looked suspicious but turned out sound are listed so they are not re-raised.

## Fixed in this pass

| # | Severity | Symptom / root cause | Fix |
|---|---|---|---|
| 1 | **Medium** (accessibility, split mode) | TalkBack's virtual-key rectangles ignored split mode. `KeyboardGeometry.computeAccessibilityKeyRects` walked each row with `physicalLeft = x + key.shift * keyWidth; physicalRight = physicalLeft + key.width * keyWidth` — neither the split **gap** (right half pushed right) nor the compensating **scale** (both halves narrowed). `keyAt`, the hit-tester every finger goes through, walks `rowSpans` and applies both. So with split on (`split_enabled`, default gap 10 %), every node on the right half named a region up to one gap (4–25 % of the keyboard width) away from the key it described, and its width was the unsplit width. Touch exploration announced the wrong key, and focus rectangles hovered between keys. The invariant was already pinned by a test — `accessibilityRectsMatchFilteredKeyAtAcrossEveryPixel` — but only with `splitGap = 0`, so it could never fail. | The walk now goes through `rowSpans(row, params)` and tracks the previous cell's right edge as the current cell's left edge, which is exactly how `keyAt` assigns the inter-key gap (and the split gap) to the key on its right. With split off the accumulation is unchanged, float operation for float operation. New test `accessibilityRectsFollowSplitGapAndScale` re-runs the every-pixel invariant with a 210 px gap / 0.79 scale and pins where the gap was applied. |
| 2 | **Low–Medium** (thread safety) | `EmojiKeywordIndex` published its trie unsafely. `prewarm()` builds a `TrieNode` graph on `Dispatchers.IO` and assigns `rootNode` / `isLoaded`; `Emoji.search()` reads them from the emoji search `TextWatcher` on the main thread. Both fields were plain (non-`@Volatile`) `var`s, so there was no happens-before edge between the write and the read: a main-thread search could observe `isLoaded == false` (returning "no results" for a query the index already contains) or, worse, a partially published trie, because non-volatile publication is a data race in the JMM. It presents as an intermittent "emoji search finds nothing until I type another letter". | `rootNode` and `isLoaded` are `@Volatile`, with the reason in KDoc. The loader assigns the fully built graph before setting `isLoaded`, so both fields now carry the necessary ordering. |
| 3 | **Low** (perf, per keystroke) | `PredictionContextTracker.normalizeForPrediction` compiled `Regex("\\p{Mn}")` on every call. That call runs twice per `synchronizeWithCursor` (prefix and suffix — i.e. on every cursor movement, app switch, and suggestion commit) and again for words committed through the tracker. `Pattern.compile` is tens of microseconds plus an allocation; the pattern is a constant. | Hoisted to `COMBINING_MARKS` in the companion and reused. Behaviour is identical (same pattern, same NFD order). |
| 4 | **Low** (perf, dictionary load) | `MainDictionarySource`'s JSON fallback compiled `Regex("^[\\p{L}'-]+$")` **inside its per-word loop**. That path is taken by any language without a packaged `*_enhanced.bin`; a `*_enhanced.json` lexicon is tens of thousands of entries, so the load paid one regex compile per word — seconds of CPU on a device, on a path that already reads and parses the whole file. | Hoisted to `VALID_WORD` in the companion; the loop now calls `VALID_WORD.matches(word)`. |

## Reported, not fixed

Each item is evidenced and actionable. They are not applied because they change timing semantics,
change the owner's chosen look, or need a finger on a device.

### F1 — floating mode can be dragged until only its grip is on screen *(Medium, UX)*

`FloatingConfig` places the window's **top edge** at `screenHeight * yFraction`
(`FloatingConfig.kt:46-47`) and caps the fraction at `MAX_Y_FRACTION = 0.9f`
(`FloatingConfig.kt:31`). Its own KDoc says the cap exists so "the keyboard can never be dragged
until only its grip shows" (`FloatingConfig.kt:15`), but the cap is a fraction of the **screen**, not
of the space left after the keyboard:

- the window's height is the keyboard's `WRAP_CONTENT` height
  (`WindowLayoutUtils.updateSoftInputWindowLayoutParams`, `:236-238`; `applyFloatingWindowLayoutParams`
  deliberately leaves it alone, `:270-271`), and the gravity is `TOP|START` with `y` as the offset
  (`WindowLayoutUtils.kt:289-297`);
- on a 2400 px-tall screen with a 38 % keyboard (≈910 px), `y = 0.9 * 2400 = 2160` puts the bottom
  edge at 3070 px — **670 px (28 %) of the keyboard, i.e. the whole bottom row including space,
  period and enter, is below the display**;
- even the default `0.62` lands the bottom edge at `0.62 + 0.38 = 1.00`, before the navigation bar
  inset is taken off, so the bottom of the space bar is already marginal on some devices;
- the value persists (`persistFloatingPosition`), so the next time the keyboard floats it comes back
  off-screen. The grip remains reachable, so it is recoverable — but the user has to find out why
  half the keyboard is gone.

**Fix sketch:** make the cap a function of the window height instead of a constant. Add
`FloatingConfig.maxYFraction(screenHeight, windowHeightPx)` = `((screenHeight - windowHeightPx) /
screenHeight).coerceIn(0f, MAX_Y_FRACTION)`, clamp the stored fraction against it in
`currentFloatingWindow()` and in `moveFloating()` (clamping only at use would leave the fraction
"stuck" above the clamp and make an upward drag do nothing until it unwinds), and pass the hosted
root's measured height. Pure arithmetic, so it is JVM-testable; the exact window height needs one
device check because it also includes the suggestion strip and toolbar.

### F2 — the default swipe trail is the most expensive effect, and it runs per frame *(Medium, perf)*

`Defaults.SWIPE_TRAIL_EFFECT = "sparkle"` (`Config.kt:175`), so this is the shipped path, not an
opt-in. `Keyboard2View.drawSwipeTrail`'s sparkle branch (`Keyboard2View.kt:2021-2072`) draws **three
blurred circles per path point** on **every frame** of the swipe, each with its own `sin`, several
float multiplies and a `drawCircle` through a paint that carries a `BlurMaskFilter`
(`initSwipeTrailPaint`, `:402-410`). The path is one point per accepted move sample
(`ImprovedSwipeGestureRecognizer.addPoint`), so a one-second word swipe is a few hundred samples:
~600–1,000 blurred circles per frame, 60 times a second, for the duration of the gesture. The
`rainbow` branch also allocates a `floatArrayOf` per frame (`:2016`).

This is the same class of cost the 2026-10-25 audit chased out of the toolbar and the suggestion
strip, on the one path where the user is actively dragging a finger.

**Fix sketch:** (a) stride the particle loop (every 2nd/3rd point) instead of drawing one set per
sample; (b) precompute the per-index pseudo-random offsets once per swipe rather than per frame
(the seeds are stable by design, so the values are too); (c) keep the blur mask off the particles
and blur only the base trail; (d) hoist the `floatArrayOf` for `HSVToColor` into a field. Any of
(a)–(c) changes the look, which is the owner's call — hence report-only.

### F3 — clipboard history constructor does database cleanup and file deletes on the caller's thread *(Medium, perf/ANR)*

`ClipboardHistoryService`'s `init` block (`ClipboardHistoryService.kt:139-160`) synchronously:

1. opens the database (`_database` → `ClipboardDatabase.getInstance` → `SQLiteOpenHelper`),
2. reads the TTL preference and either `rescueExpiredEntries()` or `cleanupExpiredEntries()`
   (a table scan plus a `DELETE`),
3. **deletes media files** for each expired row, one `File.delete()` per row,
4. and only then dispatches the orphan reconciliation to `Dispatchers.IO` (`:157`).

The service is constructed from `CleverKeysService.onCreate` → `ClipboardHistoryService.on_startup`
(`:1210`), i.e. on the main thread, during IME startup — the same startup the owner has already
reported as feeling slow. On an install with a large history (the default is unlimited) and many
media clips, that is an unbounded amount of disk I/O before the keyboard draws for the first time.

**Fix sketch:** move steps 2–3 into the `serviceScope.launch(Dispatchers.IO)` block that already
exists, ordered before `getAllReferencedMediaPaths()` so the orphan sweep sees the post-cleanup
table. The DB is thread-safe; the only behavioural change is that an expired row may survive for
the few milliseconds until the job runs. `clearExpiredAndGetHistory()` already does the same work
on demand, so nothing depends on the constructor having done it first.

### F4 — theme-editor key centres ignore split mode *(Low, latent, preview only)*

`Keyboard2View.getRealKeyPositions()` (`:1447-1491`) accumulates `x = xLeft` and applies `key.shift`
but not the split gap/scale, unlike `geometryParams()`/`rowSpans` which the tap path uses. Its only
production consumer is the Theme Creator preview (`ThemeEditorPreview.kt:154`), so the harm is a
sample swipe trail drawn away from the keys when the user has split mode on while editing a theme.
**Fix:** derive the centres from `KeyboardGeometry.rowSpans` the way `computeKeyRects` does. Left
alone because the preview is a settings surface, not the typing path, and the map's other consumer
is an instrumented test.

### F5 — the unit-test suite cannot pass, and CI never runs it *(High, process)*

`AGENTS.md` and the workflow header both say `assembleDebug` is deliberate and `test` is skipped
because upstream drift tests assert on files this fork does not vendor. That is true, but the
consequence is wider than the note admits:

- CI has **no test step at all** (`.github/workflows/build-apk.yml`), so the ~560 files under
  `src/test` and `src/androidTest` have never run in this repository's history — including the
  ratchet tests that the 2026-10-25 and 2026-10-30 hunts added as their proof, and the test added in
  this hunt.
- At least **16 test files reference paths that do not exist** in this tree, so `./gradlew test`
  cannot be green even if someone tries: `docs/RELEASE_RECORD.md` (LayoutCatalogueTest,
  ReleaseClaimNavBarTest, ReleaseClaimTextActionsTest, ReleasePackagingDriftTest,
  ReleaseRecordDriftTest, SettingsSearchCoverageTest, SuggestionTapPartialReplaceTest,
  ReleaseClaimCommandCatalogueTest), `RELEASE_NOTES.md` + `fastlane/` (ReleaseMetadataDriftTest),
  `.github/scripts/emulator-ci.sh` (CuratedInstrumentationListTest), `docs/i18n/glossary.json`
  (TranslationGlossaryTest), and `scripts/dictionaries/langpack-*.zip` (the CTC/pack tests, the
  Hebrew autocorrect evals and NoticeModelAttributionDriftTest).
- `docs/i18n/glossary.json` is also read by `scripts/export_translation_review.py`, so the
  translation-review tooling is pointing at a file that is not in the repository.

The practical cost: a change that breaks `KeyboardGeometryTest`, `SettingsRangeDriftTest`,
`ConfigSnapshotRatchetTest` or any of the other pure-JVM invariants ships silently. The two earlier
hunts both claimed "verified by unit tests" for changes that no machine ever compiled the tests for.

**Suggested fix (owner decision, because it spends CI minutes):** a second job in `build-apk.yml`
(or its own workflow) that runs a **filtered** suite instead of `test`:

```yaml
      - name: Unit tests (portable subset)
        run: >
          ./gradlew testDebugUnitTest
          --tests 'tribixbite.cleverkeys.a11y.*'
          --tests 'tribixbite.cleverkeys.clipboard.*'
          --tests 'tribixbite.cleverkeys.gesture.*'
          --tests 'tribixbite.cleverkeys.swipe.*'
          --tests 'tribixbite.cleverkeys.backup.*'
          --tests 'tribixbite.cleverkeys.prefs.*'
          --tests '*SettingsRangeDriftTest'
          --tests '*PointersSliderSpeedTest'
          --tests '*ModifiersValueSemanticsTest'
```

Gradle still compiles every test source for the task, so the first run is the real gate — it tells
us whether the suite even compiles — and the `--tests` filters keep the known-broken release-record
classes out of the verdict. Emit the summary as an annotation (the report artifacts are unreachable
from the dev sandbox, per `docs/CI-STORAGE.md`) and keep the report upload `continue-on-error`.

### F6 — small things worth a sweep, not a report each

- `CleverKeysService.get_imm()` (`:603-605`) is `_subtypeManager!!` and has **no callers** — dead
  code with an NPE waiting for its first use on the degenerate no-config startup path that
  `refreshSubtypeImm` explicitly supports (`:613-617`). Delete it or make it lazy.
- `EmojiKeywordIndex.search` logs `Log.w("Search called before index loaded")` on every keystroke
  typed in the emoji search box before the background load finishes; it is an expected state, not a
  warning, and it is on the search path.
- `Autocapitalisation.event_sent` returns before calling `callback` when `meta != 0` (`:62-67`): it
  sets `shouldEnableShift = false` and `shouldUpdateCapsMode = false`, then returns. The deliberate
  part is not re-arming shift for a Ctrl/Alt combination; the side effect is that the decision is
  only *applied* on the next unmodified key, so after a Shift+letter hardware/modifier event the
  visual shift state can lag by one key (the next character is typed unshifted, then shift clears).
  Plausible and one-tap to verify on a device; not asserted here.

  are built even when the level is filtered.

## Checked and found sound (do not re-raise)

- **`BackupCrypto` / `Pbkdf2Sha256`**: AES-256-GCM with a fresh salt+Nnonce per container, header
  bound as AAD, iteration cap enforced *before* key derivation, streaming encrypt/decrypt with
  explicit `cipher.update`/`doFinal` (no `CipherInputStream`), key bytes zeroed in `finally`. The
  hand-rolled PBKDF2 is correct (single `Mac` keyed once, `U1..Uc` XOR accumulated per block) and
  covers the API 24/25 gap where `PBKDF2WithHmacSHA256` is unavailable.
- **Clipboard SQLite paths**: every `rawQuery` in `ClipboardDatabase`/`GifDatabase` I traced closes
  its cursor (`.use { }`), and the one transaction opened by hand
  (`updateEntryContentInTable`) has both `setTransactionSuccessful` on the success path and an
  `if (db.inTransaction()) db.endTransaction()` in `finally`, so a duplicate-conflict early return
  cannot leak an open transaction.
- **`Pointers` deferred-down bookkeeping**: the tap-vs-gesture decision re-checks
  `FLAG_P_DEFERRED_DOWN` per branch, cancels the long-press before the tap commit, and the
  backspace/nav-subkey paths both clear the flag before falling through to classification — no
  double-emit or dropped key found in the deferred paths.
- **`SuggestionBar` view pool**: click/long-press closures capture the **pool slot** index, and
  `reconcileChildren` only ever reorders the pool in slot order, so a recycled view cannot dispatch
  the previous suggestion's word. The temporary-message path suppresses suggestion writes while it
  is up, which is what keeps that invariant.
- **`KeyboardData` parsing**: `load`/`load_string` both catch and fall back (a malformed custom
  layout cannot take the IME down), and `add_key_to_pos`/`add_key_to_preferred_pos` bound every
  index by `minOf(row, rows.size - 1)` / `row.keys.size - 1` before indexing.
- **`SubkeyPopoverGeometry.gridCentre`**: the `viewSize <= 2 * half` guard runs before
  `coerceIn(half, viewSize - half)`, so the reversed-range `IllegalArgumentException` is not
  reachable; `slotAt` returns `null` for non-positive cell sizes.
