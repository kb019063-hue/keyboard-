# Keyboard bug hunt — 2026-10-30

## Why this hunt exists

The owner asked for a hunt over the whole repository — "bugs, flaws, issues, performance issues,
etc" — without naming a symptom. The previous hunt ([`BUG-AUDIT-2026-10-25.md`](BUG-AUDIT-2026-10-25.md))
started from a green CI run and worked outwards from the harness; this one started from the code
paths that are hardest to get right and least covered by the ratchet tests: the touch/gesture
state machine, the clock reads around it, the preference layer that feeds it, and the Binder
traffic on the typing path.

Two rules were applied throughout:

1. **A finding needs an executed path and a stated harm.** Anything I could not trace to a
   caller is labelled "latent" instead of being dressed up as user-visible.
2. **Owner decisions are off-limits.** Default layout, default theme, the seven-button toolbar,
   the migration markers, and the fixed bugs in the 2026-10-25 audit were treated as constraints,
   not as candidates.

Seven defects are fixed on this branch. Six more are reported with evidence and a fix sketch but
not applied, and a larger set was checked and found sound so it is not re-raised later.

## Fixed in this pass

| # | Severity | Symptom / root cause | Fix |
|---|---|---|---|
| 1 | **High** | The space-slider speed multiplier started at its **maximum** and stayed there. `Pointers.Sliding.update_speed` computed the finger speed as `travelled / (now − last_move_ms)`; `last_move_ms` was seeded from the sample *at* the move that began sliding, so the first division was `x / 0 = +Infinity`, and the multiplier is `min(slider_speed_max, …)` — which is `slider_speed_max` for any non-zero travel. `slider_sensitivity`, the smoothing factor and the speed ceiling were all dead: the cursor always slid at the ceiling. `+Infinity` also poisoned the exponential smoother, because `smoothing * ∞` never leaves `∞`. | The estimate is now the pure, unit-tested `Pointers.smoothedSpeed(previous, travelled, elapsedMs, maxSpeed, smoothing)`, which returns `previous` for `elapsedMs <= 0` (also covers a backwards clock step) and otherwise applies `min(maxSpeed, travelled / elapsedMs * scale)` behind the ceiling. `Sliding.update_speed` calls it. |
| 2 | **Medium** | Wall-clock reads on the input path. `Pointer.downTime`, the SWIPE/TAP elapsed time and `Sliding.last_move_ms` used `System.currentTimeMillis()`, and so did the double-space detector's `currentTime`. A device time update (NTP, DST, manual change) that moves the clock backwards makes elapsed negative: the double-space gap test fails (two spaces stop producing a period), the SWIPE-before-TAP ordering flips, and — with `downTime` — the slider speed goes negative, which now feeds a `min()` too. | All five reads use `android.os.SystemClock.uptimeMillis()`, which is monotonic and immune to time updates. |
| 3 | **Medium** | Selection-delete (swipe-and-hold backspace, GH #190) behaved **inversely** at the top of its own slider range. The vertical normalisation divided by `maxDistance − verticalDeadZone`; with the default key height (≈0.7 × hypotenuse) the dead zone's 80 % setting is ≈56 % of the half-diagonal, so the span went to zero or negative — a bigger vertical drag produced a *smaller* normalised value, i.e. a faster finger repeated *slower*. Separately, `selection_delete_vertical_speed = 0` (importable, see #4) made the repeat interval `x / 0 = Infinity`, and `Infinity.toLong()` saturates to `Long.MAX_VALUE`: the repeat never fired at all. | New pure seam `Pointers.selectionDeleteVerticalNormalized(absDy, deadZonePx, maxDistancePx)`: the span is floored at 10 % of `maxDistance`, non-finite/zero spans return `0f`, and the result is `coerceIn(0f, 1f)`. The divisor is sanitised at the call site. |
| 4 | **Medium** | Four gesture preferences feeding those divisions had **no shared range, no read clamp, and no import validation**: `slider_speed_max`, `slider_speed_smoothing`, `selection_delete_vertical_threshold`, `selection_delete_vertical_speed`. A backup import (or a hand-edited prefs file) could set the smoothing to 0 (estimate never moves), the ceiling to 0 or negative (the multiplier goes *negative* and the cursor slides the wrong way), the dead zone outside 20–80 %, or the speed to 0 (no repeat). Only the sliders themselves were range-limited, so the UI was the only guard. | Added `SettingsRanges.SLIDER_SPEED_SMOOTHING` (0.1–0.95), `SLIDER_SPEED_MAX` (1–10), `SELECTION_DELETE_VERTICAL_THRESHOLD` (20–80), `SELECTION_DELETE_VERTICAL_SPEED` (0.1–1) with the bug history in their KDoc; `Config.refresh()` clamps every read (NaN falls back to the default), `SettingsPersistence` clamps on load, `SettingsValidation` gained the int/float import branches (plus the float-percentage allowlist entry), and `GestureTuningSection` now passes `SettingsRanges.….toSliderRange()` directly instead of four hand-copied local ranges — one definition per bound. |
| 5 | **Medium (perf)** | Every punctuation keystroke did **two Binder round trips before it could decide anything**: `getTextBeforeCursor(500, 0)` plus `PredictionContextTracker.currentSelection(conn)` (a full `getExtractedText`). Both exist only to prove a pending auto-space may be swallowed — and the pending flag is a local field. On an ordinary punctuation press (no auto-space pending) both reads were pure cost, on the per-keystroke path, against the editor's process. | The local flag is consulted first and the block is skipped entirely unless it is set. The verify-at-use reads still run whenever an answer can actually be "yes", so the security property (verify at use, never trust the flag alone) is unchanged. |
| 6 | **Low** | `Pointers.Modifiers.equals`/`hashCode` compared the **whole backing array**, but the array is normally longer than `size()`: `getModifiers()` allocates one slot per pointer and `ofArray` compacts into a prefix without shrinking. Two Modifiers with identical modifiers were therefore unequal whenever they came from different pointer counts — most visibly, `getModifiers()` with one finger down and nothing latched (length 1, size 0) did **not** equal `Modifiers.EMPTY` (length 0). `KeyModifier` memoises `modify()` on this type and its KDoc explicitly promises content equality, so the dead tail broke memo hits and split one logical modifier set across several map entries. | `equals`/`hashCode` now cover `0 until size()` only, with the reason documented. New `ModifiersValueSemanticsTest` pins the three cases (dead tail ignored, empty-from-live-pointer equals `EMPTY`, different modifiers stay unequal). |
| 7 | **Low (latent)** | `Keyboard2View.isPointWithinKeyWithTolerance` advanced its running x by `k.width` only, while the canonical layout loop (`getRealKeyPositions`) advances by `shift + width`. Every key *after* a shifted key in a row was tested against the wrong x. The layouts that inset keys this way are all non-Latin (`arab_pc`, `beng_national`, `deva_*`, `cyrl_yaverti`, `georgian_*`, …). It is latent rather than live because nothing in `src/main` calls the helper — and the token tests that stub the interface return `true` unconditionally, which is exactly why the bug could never surface there. | The accumulation now matches the canonical loop (`(k.width + k.shift) * _keyWidth`). |

## Reported, not fixed

Each of these is evidenced and actionable; I left them alone because the fix either needs device
testing, changes timing semantics across the app, or should be an owner call.

### N1 — `swipe_dist` has no range anywhere, and it gates tap-vs-gesture *(Medium)*

`Pointers.kt:1053` starts gesture handling with `if (dist >= snap.swipe_dist_px && …)`.
`Config.kt:1302-1303` maps the preference with `swipe_dist_value / 25f * swipe_scaling` and never
clamps it. The settings slider is 5–30 (`ui/settings/sections/InputBehaviorSection.kt:389`), so the
UI is the only guard — and the import validator
(`backup/SettingsValidation.kt:559`) accepts any non-negative number, including `"0"`.

- `0` (or a tiny value): `dist >= 0` is true on the first move sample, so a tap with ordinary
  finger jitter enters the subkey/gesture branch, where `getNearestKeyAtDirection` can activate a
  slider or an event subkey the user never meant to touch.
- A large value (e.g. a corrupt `99999`): no swipe ever reaches the threshold, so swipe typing,
  short swipes and slider activation all stop working while tapping still does.

**Fix:** add `SettingsRanges.SWIPE_DIST = 5..30`, clamp the read in `Config.refresh()` and in
`SettingsPersistence`, and range-check the string branch in `SettingsValidation.validateString`
exactly the way `clipboard_history_limit` already does (`SettingsValidation.kt:555-556`) — then add
the sites to `SettingsRangeDriftTest`'s ratchet so they cannot drift apart again.

### N2 — one full `Config.refresh()` per preference write, on the writer's thread *(Medium, perf)*

`ConfigurationManager.onSharedPreferenceChanged` (`ConfigurationManager.kt:130-137`) ignores `key`
and calls `refresh(context.resources)` unconditionally. `refresh()` re-reads the whole preference
set and then fans out `onConfigChanged` to every registered listener; a theme/style change adds a
second fan-out of `onThemeChanged`, which recreates views. Because `SharedPreferences` listeners
fire on the thread that wrote, a slider drag in Settings produces N refreshes on the main thread
where one would do — and each refresh allocates a new `Config` plus a `ConfigSnapshot`.

**Fix:** coalesce. Post the refresh to the main `Handler` and `removeCallbacks` any pending one
first (or accumulate a dirty-key set and refresh once per frame). Both preserve "config is
eventually fresh" while collapsing a drag to a handful of refreshes. Not applied here: the whole
app's listeners assume a refresh per write, so the change wants its own CI run and a look at
`ConfigurationManagerTest`/`ConfigSnapshotRatchetTest`.

### N3 — "Select word" truncates at 50 characters and trusts a second IPC for its offsets *(Low-Medium)*

`Keyboard2View.kt:1295-1320`. The word boundaries come from `getTextBeforeCursor(50, 0)` /
`getTextAfterCursor(50, 0)`, and the absolute positions are then derived from a *separate*
`getExtractedText` call:

- a token longer than 50 characters (URL, base64 blob, long hashtag) yields a span that stops at
  the window edge, so "select word" silently selects a fragment of it;
- the two reads are not atomic, so if the editor's text or cursor changes between them the
  `setSelection(wordStart, wordEnd)` uses offsets that no longer describe the word that was
  measured. The failure is a wrong selection, and with a subsequent key press, a wrong replacement.
- The `else` fallback's comment promises "Ctrl+Shift+Left then Shift+Right", but only the
  Ctrl+Shift+Left pair is ever sent.

**Fix:** take the window and the cursor from one `getExtractedText` result (the code already has
`EditorTextWindowReader` for exactly this), raise the window to `EditorTextNavigation.WORD_REACH`,
and either implement the promised shift+right or delete the claim. Not applied: selection behaviour
differs per editor and needs a device pass.

### N4 — `slider_sensitivity` import range-check is stricter-looking than it is *(Low)*

`SettingsValidation.kt:548` validates with `Regex("[0-9]+")`, so `"0"` and `"999999"` import
cleanly, even though `SettingsRanges.SLIDER_SENSITIVITY_PERCENT` is `1..100` and `Config.kt:1307-1311`
clamps the read. Because `SettingsPersistence.kt:207` does **not** clamp, the Settings screen then
displays the imported value while the keyboard uses the clamped one — the slider lies about the
effective setting.

**Fix:** mirror the `clipboard_history_limit` branch: `value.toIntOrNull()?.let { it in
SettingsRanges.SLIDER_SENSITIVITY_PERCENT } == true`, and clamp in `SettingsPersistence`.

### N5 — `addClip` still throws on a cold start, and the failure is reported as a clipboard error *(Low)*

`ClipboardHistoryService.addClip` (`:405-409`) calls `Config.globalConfig()`, which throws
`NullPointerException` when the IME never ran — while its own `storeClip` (`:445`) deliberately uses
`globalConfigOrNull()` for exactly that case ("PROCESS_TEXT / editing-key … where the IME never
ran"). `captureClip`'s broad `catch (e: Exception)` then logs "Clipboard read failed
(NullPointerException)" and drops the clip. `captureClip` has two more throwing reads at `:917`
(`clipboard_exclude_password_managers`) and `:942` (`clipboard_respect_sensitive_flag`) inside the
same try.

**Fix:** use `Config.globalConfigOrNull() ?: return` in `addClip`, and the same null-safe read for
the two policy flags (falling back to the documented defaults, as `storeClip` does). Behaviour for an
initialised Config is identical.

### N6 — 383 unguarded `Log.d` and 126 `Log.i` in a debuggable debug build *(Low, perf/log hygiene)*

The installed app is the **debug** variant (`debuggable true`, `minifyEnabled false`) and
`ENABLE_VERBOSE_LOGGING` is `false`, so the `if (BuildConfig.ENABLE_VERBOSE_LOGGING)` guards and the
60 `vlog {}` lambdas (which avoid evaluating their message) are all correct — but 383 `Log.d`, 126
`Log.i`, 220 `Log.w` and 266 `Log.e` call sites remain unguarded. Every one of them evaluates its
interpolated message eagerly, even though the level is dropped in release and mostly filtered in
logcat: on the touch path that is a string allocation per event for a message nobody reads.

**Fix:** a mechanical sweep of `Log.d`/`Log.i` to `vlog { }` (or to the guarded form) in the hot
files (`Pointers.kt`, `Keyboard2View.kt`, `KeyEventHandler.kt`, `InputCoordinator.kt`), plus a
`tools/check_logging.py` gate so new unguarded calls fail the build the way `check_layout.py`
already does.

### N7 — notes for the owner (information, not defects)

- **Clipboard storage has no total budget.** `clipboard_history_limit` defaults to unlimited and a
  media clip is capped per item (`clipboard_max_media_size_mb`, 1–50 MB), not in aggregate; media
  files live in `filesDir`, so a heavy user accumulates without bound. A total-size sweep (or a
  "storage used" line in Settings → Clipboard) would close it. This follows the owner's documented
  "keeps everything indefinitely" decision, so it is reported, not changed.
- **Backup restore cannot undo learned n-grams.** `BackupRestoreManager.kt:2153` carries
  `TODO(CK-150-020)`: import writes learned bigrams/trigrams and the user vocabulary outside
  `prefs`, so the snapshot rollback that protects the rest of an import cannot reverse them. A
  partial import therefore leaves learned data behind.
- **Accepted risk, already documented: `BackupRestoreActivity` is exported.** Any installed app can
  send `EXPORT_CLIPBOARD` with a `content://` or `file://` URI it can itself read, which makes the
  clipboard history readable by a third party that holds no permission. The #70 Termux automation
  requirement means this cannot simply be `exported="false"`; the mitigations in place are the 2 s
  rate limit (`MIN_HEADLESS_ACTION_SPACING_MS`) and caller logging. Worth a line in the README's
  threat section so it is a decision rather than an oversight.
- **`Autocapitalisation.event_sent` returns early when `meta != 0`** (`Autocapitalisation.kt:62-67`)
  without calling `callback(true)`. The shift suppression looks deliberate (a modified key must not
  re-arm autocap); the missing callback means a modified key never refreshes the caps state either.
  Flagged for a device check, not asserted as a bug.

## Checked and found sound (do not re-raise)

`PathScorer` — every divisor is guarded (`lengthRatioPenalty` returns 0 for a non-positive
template) and `GeometricEngineConfig.init` fails fast on every sigma/weight that could produce NaN
(`shapeSigma`, `locationSigma`, `lengthRatioSigma`, `softmaxTemperature`, …), so the geometric
engine cannot be configured into a division by zero.

`GestureRecognizerTypes.RawSwipeTrace.withLift` — the `timestamps.last()` call is behind
`points.isEmpty() || points.size != timestamps.size`.

`Pointers.Modifiers` array elements (`_mods[i]!!`) — `ofArray` sorts nulls last and compacts them
out, and every construction path goes through it, so the live prefix is never null.

`DictionaryDataSource.cachedWords!!` — each use is immediately preceded by a null check on the same
thread; the double-checked shared cache is `synchronized`.

`LayoutsPreference.unsafeLayoutIdsStr/unsafeLayoutIdsRes!!` — written immediately before use in the
same call.

`BackupRestoreActivity`'s `runBlocking` in `BackupRestoreManager` (`:861/:916/:946/:2125`) — every
caller wraps it in `withContext(Dispatchers.IO)`, so it blocks an IO thread, not the main thread.

Backup coverage of learned data (`:1196`, `:1249`) — bigrams, trigrams and the user vocabulary now
ride the dictionaries payload; the earlier "backup blind spot" is closed.

Clipboard philosophy: `rewriteSystemClipboard`, `clearPrimaryClipboard`, `insertGif`, the receiver
pairing, `ClipboardDatabase` cleanup, `safeGet*`/`repairCorruptedFloatPreferences`,
`handleTimestampKey`, `FloatingConfig`, `ClipboardHistoryView`, `KeyboardMinimizer`, `SmartAutoSpace`,
and the suggestion-bar view recycling are all correct; none of the 2026-10-25 fixes has regressed.
