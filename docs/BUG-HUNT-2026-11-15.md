## H1. The clipboard's delete path trusted a path from a backup file, and `File.delete()` happily removes a directory

**What this is.** `ClipboardMediaManager.deleteMedia(mediaPath)` resolved its argument with a bare
`File(context.filesDir, mediaPath)` and deleted whatever was there. The only other reader of a
stored `media_path`, `getMediaFile`, has done a canonical-path containment check since the zip-slip
hardening; `deleteMedia` never got one. Its own KDoc calls deletion callers "post-commit
reference-checked media cleanup", which is true of the *reference check* (is another table still
using this path) and says nothing about *where the path points*.

**Why the argument is untrusted.** `ClipboardDatabase.importHistoryEntries` writes
`entry.optString("media_path")` from a backup ZIP into `media_path` verbatim. Every route that
removes a row then hands that string back to `deleteMedia`: `removeClipboardEntry`, `unpinEntry`,
`removeFromTodo`, `deleteSnapshot`, `clearHistory`, and both storage-limit prunes
(`applySizeLimit`, `applySizeLimitBytes`). So a backup file with a row whose `media_path` is
`databases/clipboard.db` — a plain `filesDir`-relative path, no `..` needed — has its target
deleted the first time that entry leaves the list, or the first time a limit prunes it.

**Measured, not assumed.** Both bodies were run against real directories in this sandbox — a
Python model of each, with `File.delete()` modelled as Java defines it (a directory is deleted only
if empty; it never throws) — because the interesting failures are ones where Java differs from the
obvious guess:

| `media_path` written by the backup | old `deleteMedia` | fixed |
|---|---|---|
| `databases/clipboard.db` | **deleted**, then pruned the emptied `databases/` | refused |
| `clipboard_media/../../cleverkeys.db` | **deleted** — that is the package directory, *outside* `filesDir` | refused |
| `clipboard_media` (empty) | **deleted it, then pruned `filesDir` itself** | refused |
| `clipboard_media` (holds `042/keep.png`) | nothing (delete fails on a non-empty dir) | refused |
| `clipboard_media/042` (empty) | **deleted it, then pruned the emptied `clipboard_media/`** | refused |
| `clipboard_media/042` (holds `keep.png`) | nothing (same reason) | refused |
| `clipboard_media/007/abc.png` (a real entry) | deleted, emptied partition pruned | unchanged |

The third row is the one that turned this from "a crafted backup can delete a file" into "a
crafted backup can delete the app's files directory". `File.delete()` on a directory returns
`false` when it is non-empty and succeeds when it is empty, so the old cleanup branch — "if the
parent is now empty, remove it" — ran on `filesDir` for a row whose path was just
`clipboard_media`, and `filesDir` is empty on a first run. (`filesDir` being recreated lazily by
the platform means this is probably not fatal, but it takes every database and preference file with
it, and the clipboard history is gone.)

The fourth and sixth rows are why `exists()` was not the right gate and `isFile` is: a partition
directory passes the containment check, so the old method would attempt to delete it, and the
cleanup branch would then delete the media directory above it.

**The fix.** Route the path through the existing `getMediaFile`, whose `SecurityException` is
caught and logged as a refusal (a bad row must not make a delete throw), gate the delete on
`isFile`, and gate the partition prune on a comparison against the media directory's *canonical*
path. Canonical matters: `getMediaFile` returns a canonical `File`, while `filesDir` is not
guaranteed to be one (`/data/user/0/<pkg>/files` is reached through a symlink on some devices), so
a plain `File` equality would compile, pass on the test's temp directory, and silently never prune
on a device. The first draft of this fix had exactly that bug.

**Tests.** Five new cases in `ClipboardMediaManagerZipSlipTest`, which already builds a manager
over a real temp directory with a mocked `Context`: the plain relative path, the `..` escape (a
second manager over a nested `pkg/files` layout, since the victim has to be a sibling of
`filesDir`), the media directory, `filesDir` under the collapse, an empty partition — and two
controls that must keep passing (a real file is deleted and its emptied partition pruned; a
partition with another entry in it is kept). Each of the five refusals fails against the old body
and each control passes against both, so the set pins the fix rather than pinning "deletion
happened to stop working".

## H2. The GIF pack importer had no bound on what a ZIP could expand to

**What this is.** `GifPackManager.extractZip` walked a user-chosen ZIP and called
`ZipInputStream.copyTo(fos)`. Nothing capped the number of entries or the number of bytes written;
`copyTo` runs until the entry ends, and a ZIP's declared sizes are the attacker's to choose. Its
only guard was a canonical-path check per entry (path traversal), which is necessary and does not
bound size.

**Why it matters here specifically.** The import starts from a file picker or a share intent, so
the archive is arbitrary. A deflated megabyte of zeros expands to about a gigabyte, and the
extraction target is `cacheDir` — shared with the rest of the app and, on a phone with a full data
partition, with everything else that needs room. The language-pack importer
(`LanguagePackManager.importFromStream`) has had exactly these two bounds since the v1.1.96 OOM
fix, and its KDoc says so; this importer was written to the same pattern but only inherited the
half that stops path traversal.

**The fix.** `extractZip` moves to a companion `extractZipBounded`, which streams each entry in
fixed-size chunks and stops at 250,000 entries or 1 GiB extracted. Both limits are far above the
largest pack the pipeline builds (a 130k-GIF pack is ~130k thumbnails of 2-4 KB) and far below the
tens of thousands of entries a bomb uses. The refusal is a `ClassifiedIoException` carrying
`IoFailureReason.TOO_LARGE`, so the settings screen says "too large" rather than the generic
"could not read the file" an `IOException` maps to by default.

The same move tightened the traversal check by one character. It read
`target.startsWith(base)`, which is true for a sibling directory whose name merely begins with the
destination's name (`<tmp>/out-evil` for destination `<tmp>/out`). It now accepts `target == base`
or `target.startsWith(base + File.separator)` — the form `ClipboardMediaManager.getMediaFile`
already uses. This is not exploitable through the current call site (the destination is a
`cacheDir` child named `gif_pack_import_<millis>`, and the archive cannot ask for one), so it is
hardening rather than a fourth fix, and it gets no test of its own: every `../` case was already
refused by both forms.

**Tests.** Three cases in `GifPackThumbnailValidationTest`, which is already in the
`runMockTests` list: an archive that expands past the byte budget, one with more entries than the
budget, and a normal two-entry archive that extracts completely. The budgets are parameters
(defaulting to the real ones) so the cases run on kilobytes, not a gigabyte. Each fails on the old
body — which had neither bound — and the third would still pass, which is what makes it a control
rather than a duplicate.

## H3. A line holding only a bullet was joined onto the line above it

**What you would have seen.** In the clipboard pane's Clean action, a list item that is a lone
bullet — a placeholder in a template, an empty checkbox item — was pulled up onto the previous
line. `"Here is the shopping list:\n- \n- apples"` came out as
`"Here is the shopping list: -\n- apples"`, so the bullet that used to start a line now ends one,
and the item it belonged to is gone.

**Why.** `clean()` strips trailing whitespace from every line before joining them, so the lone
bullet arrives at the join decision as the single character `-`. The bullet pattern is
`^[-*+•…]\s` — it requires the space that was just removed — so `isStructural` said "prose", and
the joiner did what it does to prose: replaced the line break with a space. The other structural
patterns share the same assumption (`12. `, `[x] `, `## `); only the bullet can also stand alone.

**The fix.** A second pattern for the bare bullet, consulted by `isStructural` beside the first.
One space was removed from the output, which is what the cleaner's own contract says should happen
to trailing whitespace; the break now survives.

**Test.** `aLoneBulletLineStaysAStructuralBreak` in `ClipboardTextCleanerTest`, which also pins
that `well - known` is still prose (a hyphen alone in a line of text must not become structural).

## H4. `getClipboardStatus()` returns English to the user (reported, low)

`ClipboardHistoryService.getClipboardStatus()` builds three user-visible sentences in Kotlin
("Clipboard history disabled in settings", "Clipboard access requires setting this keyboard as
default input method", "Clipboard monitoring active (%d entries)"). `HardcodedUiStringTest` does
not flag them because its sink list keys on named parameters (`text =`, `message =`) and a bare
`return` is not one. The method has one caller, in the instrumented `ClipboardHistoryTest`, and no
production UI reads it today, so nothing is showing this to anyone yet — which is exactly why it is
worth moving to `strings.xml` before something does. Low.

## H5. Thumbnail import is bounded by the archive's own layout (reported, low)

`GifAssetManager.importThumbnails` walks every `.webp` under the extracted `thumbs/` tree and
copies each one into the app's own storage. H2's byte cap bounds the bytes written *during
extraction*; this step writes them a second time, and its file count is whatever the archive
contains, up to the 250,000-entry cap. A pack that clears the caps can therefore still double the
storage cost and spend a long time copying. The honest fix is to bound the copy count against the
manifest's `gif_count` (which the importer already parses and prints), and that needs a decision
about what to do with the rows that then have no thumbnail behind them — the blank-tile problem
ARC-038 exists to prevent. Not changed.

## H6. A suggestion tap compiled a regex to strip a literal prefix

`SuggestionHandler` stripped the decoder's `raw:` marker with
`word.replace(Regex("^raw:"), "")` on every suggestion tap, and `MLDataCollector` did the same for
every recorded swipe trace. The prefix is literal — `removePrefix` is the whole operation — so each
call compiled a `Pattern` and matched it to do what two `String` ops do.

Both now use one `internal const val RAW_PREFIX` on `SuggestionHandler`, and the four other call
sites that read or strip the same marker (`SuggestionSpanPolicy`, plus three more in
`SuggestionHandler` itself) use it too, so none of the six can drift apart. `MLDataCollectionToggleTest`
already asserts the recorded label is the bare word, and `SuggestionSpanPolicyTest` asserts the
span's alternatives have the marker stripped, so both paths stay pinned by behaviour;
`RawPrefixSingleDefinitionTest` (new, in `runPureTests`) fails if any production file spells the
prefix out again — it counts the literal across the whole of `src/main`, so a new spelling anywhere
is caught, not just the three shapes known today.

The `startsWith` at the top of the same branch was already correct (no regex there); it is rewritten
against the constant for consistency, not for speed.

## H7. Two KDoc comments describe a `raw:` producer that no longer exists (reported, low)

`Suggestion.kt` says the `raw:` marker is "produced deep in `onnx/PredictionPostProcessor`", and
`swipe/geometric/SwipeDecodingEngine.kt` refers to `PredictionPostProcessor.Result`. That file does
not exist in the tree — `ls src/main/kotlin/tribixbite/cleverkeys/onnx/` is `ModelLoader.kt` alone —
and ADR-011 deleted the neural engine's implementation. Whatever still emits `raw:` (the instrumented
`PipelineCharacterizationTest` feeds one in directly, and `SuggestionHandler` is careful to handle it)
is not that class, and a reader following the comment lands on nothing.

This is not cosmetic drift of the kind `DeadPlumbingDriftTest` already pins for removed *symbols*:
it is the only documentation of where the wire marker comes from, and it points at a deleted file.
Low, and reported rather than guessed at — replacing it needs the author's answer to "who emits
this today", which is a question about the decoder, not about this pass.

## Smaller notes (reported)

- **`ClipboardEntry.dateFormat()`** builds a fresh `SimpleDateFormat` per clipboard row, on every
  `getView()`. Rows are recycled at scroll speed. It is deliberate (the KDoc explains: no sharing
  across threads, and the user's locale is honoured if it changes), but a per-thread instance
  would have both properties without the allocation.
- **`GifDatabase.searchGifs`** calls `countFtsResults` for each candidate split of a compound word
  (up to `len-6` queries) before running the real query. It is the documented offset-independent
  rule from audit E-3 and is correct; on a 130k-row pack it is also a burst of full FTS scans per
  first keystroke. A single `LIMIT 1` probe per split would answer the same question.
- **`AnimatedCache`** in `ClipboardHistoryView` is an unbounded `mutableMapOf<Long, Boolean>`
  pruned only on page change. Bounded in practice by the entries the user scrolls through; worth
  knowing if it ever shows up in a heap dump.
- **`ClipboardHistoryView` rows** bind a whole `SpannableStringBuilder` of the entry text for a
  `maxLines="1"` view. Correct, and the cleaner's `SpannableStringBuilder` is already the cheaper
  form; leaving it alone.

- **`DebouncedPersister.flush()` does not reschedule after a failure.** The `catch` restores
  `dirty = true` and resets `firstDirtyAtMs`, but the `pending` future was cancelled at the top of
  the same method, so nothing will run again until the next `markDirty` (the next keystroke) or an
  explicit `flush()`/`requestFlush()` (teardown). On an idle keyboard the last burst before the
  failure can therefore stay unwritten for as long as the process lives. Retrying from inside the
  `catch` is not obviously right either — a persistent failure (full disk) would spin — so the fix
  is a decision (retry with backoff, or bound the retries), not a patch. Reported, not changed.

## Checked and found sound

- **The backup crypto** (`backup/crypto/BackupCrypto.kt`) — AES-GCM with the whole 51-byte header
  as AAD, a fresh salt and nonce per container (so nonce reuse is structurally impossible),
  PBKDF2-HMAC-SHA256 at 600k iterations, key bytes zeroed in a `finally`, and an explicit
  in-memory cap before `doFinal`. No change needed.
- **The language-pack importer** — entry cap, per-member byte cap, total cap, code validation
  against a regex plus a canonical-path containment check, manifest checked before anything is
  applied.
- **`SwipeCorrectionStore`** — every map it grows is evicted (200 words per language, 8 sources per
  word, 500 declines), all public methods are `@Synchronized`, and the JSON parse degrades to empty
  on anything malformed.
- **`DebouncedPersister`** — the dirty flag is restored when the flush throws, the flush is
  serialized so "flush() returned" means "the write completed", and `requestFlush` falls back to an
  inline flush when the scheduler is gone. One hole is noted below (a thrown flush is not
  rescheduled); the rest of the class holds up.
- **`ClipboardSearchUtils.compileRegex`** — bounds pattern length and the product of counted
  repetitions before compiling with RE2/J, which is linear-time by construction.
- **The thumbnail cache in `ClipboardHistoryView`** — count-bounded, evicted on tab switch, and the
  animation probe is memoized per row (the earlier `getView` cost twice noted in D-6).

## What this pass did not do

The scripts above ran; the tests ran in CI (4834, none failing). What nobody did is look at the app
on a device: no screen was touched, no keyboard typed on, and the emulator smoke is a boot-and-adb
check rather than an interaction test. The two filesystem behaviours were also modelled in Python
against real files, before any test was written, to check the old and new bodies differ in the way
the tests assert — with `File.delete()` modelled as Java defines it, which is how the `filesDir`
collapse in H1 was found. That modelling caught two wrong claims in the first draft of this report
and two tests that would have passed against the old code; the versions here are the measured ones.

Four of the five test classes touched were already registered in `build.gradle`
(`ClipboardMediaManagerZipSlipTest`, `GifPackThumbnailValidationTest`, `ClipboardTextCleanerTest`,
`MLDataCollectionToggleTest`). The fifth, `RawPrefixSingleDefinitionTest`, is new and was added to
the `runPureTests` list, so a green CI run does exercise all of them.

Not hunted this pass: the swipe decoders below the adapters, the settings screens' persistence
layer, the emoji grid's data build, and the ONNX session lifecycle.
