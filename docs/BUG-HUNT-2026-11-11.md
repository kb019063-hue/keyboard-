## 1. `main` did not build

**What happened.** PR #26 ("Fix bugs, flaws, and performance issues across the codebase") was
merged at `51c9107` five seconds after it was opened and 28 seconds after its branch was pushed
(pushed 01:21:29Z, opened 01:21:52Z, merged 01:21:57Z). The branch's own build failed at
01:23:01Z. All three workflows then failed on `main` (Build APK 42938427740, Emulator smoke
42938427786, Full unit-test suite 42938427617). The last green commit was `0e2dce4` (PR #25).

**Why it did not compile** — errors in three files:

| File | Error |
|---|---|
| `AsyncDictionaryLoader.kt` | `com.google.gson.stream.JsonParser` does not exist (Gson's parser is `com.google.gson.JsonParser`); `IOException` used without an import; a bare `return` inside a lambda |
| `CleverKeysService.kt:1171`, `:1265` | `_resources` and `foldableUnfolded` are not members of the service — neither name is declared anywhere it could resolve from |
| `KeyboardReceiver.kt:315` | the same two names, read through the service, plus the service's **private** `_config` |

CI printed the first eight diagnostics and nothing about the rest, so `KeyboardReceiver.kt` and
the second site in the service never appeared in the run (see finding 4).

**What it cost.** The rolling `dev-builds` APK never updated — it stayed the `0e2dce4` build — so
the installed keyboard was unaffected. But nothing new could ship, and every new session branched
from a tree that could not be built.

**The fix is a full revert** of the merge. The reverted tree is byte-identical to `0e2dce4`
(tree `c78838c`), the last commit on which all three workflows and the nightly passed.

**Why nothing from PR #26 was kept.** For the record, so it is not re-applied piecemeal:

- *Backup import.* `scanFileIntoMediaStore` lost its wait for the media scanner, but the next two
  lines still query MediaStore straight away — before the scan can have indexed the file. That
  step exists for backups created or modified outside the app, and it could no longer find
  anything the step before it had not.
- *Clipboard start-up.* `ClipboardHistoryService` narrowed `catch (Throwable)` to
  `catch (Exception)` in a block whose own comment says a failure there must not abort service
  construction. An `Error` there (a `NoClassDefFoundError`, say) would have escaped the
  constructor, which runs during keyboard start-up. This repository catches `Throwable` at such
  seams on purpose.
- *The "streaming" JSON parser* was not streaming: it built the whole tree in memory, never
  closed its reader, ended the trace section twice on the failure path, and looked each word's
  frequency up under its lower-cased spelling, so a capitalised entry got none.
- *The one-handed "fix"* rested on a wrong premise. See finding 2.
- *The changelog listed two changes the diff did not contain* — a `finally` cleanup and passphrase
  wipe in `decryptZipToTempFile`, and "restored full V1/V2 parsing logic" with new safety checks
  in `BinaryDictionaryLoader`. Neither is in the diff.
- The rest (catch blocks split into identical arms; a trace condition that is always true for
  bundled dictionaries, which are all named `<lang>_enhanced.bin`) changed nothing.

## 2. The open keyboard could apply a setting one change late

This is the real defect behind the "one-handed tool stuck" fix that PR #26 attempted.

**PR #26's explanation was that the preference listener had not fired yet.** It had. On the main
thread, `SharedPreferences.Editor.apply()` calls every listener before it returns
(`SharedPreferencesImpl.apply()` ends with `notifyListeners(mcr)`).

**The actual weakness: two listeners that depended on each other.**

- `ConfigurationManager` was one listener. It refreshes `Config`.
- `CleverKeysService` was a second, separately registered listener. Its
  `onSharedPreferenceChanged` drives `PreferenceUIUpdateHandler` — the one-handed root, the
  toolbar, the suggestion strip's opacity — plus floating, strip height and split. **All of it
  reads `Config`.** For the one-handed root this was the *only* path that updates an open
  keyboard.

So the service needed the manager to have run first, and two things broke that:

1. **Android gives no order.** `SharedPreferencesImpl` copies its listeners into
   `new HashSet<>(mListeners.keySet())`, and `mListeners` is a `WeakHashMap`. Which of two
   listeners runs first depends on object hash codes, so it can differ from one process start to
   the next. (Checked in the `android-7.0.0_r1` and `android-14.0.0_r1` sources.)
2. **The burst coalescing from 2026-10-31.** For any write within 150 ms of the one that began a
   burst, the manager postpones its refresh by 100 ms. The service's listener still ran
   immediately, against a `Config` that had not been refreshed, and was never run again when the
   trailing refresh finally happened.

Either way the open keyboard applied the value from *before* the change. And one-handed mode's
stop control could not recover: it writes `false`; if the stored value is already `false`,
`SharedPreferencesImpl` reports no change at all, so no listener runs and nothing re-applies the
state.

**Reproduced in a model, not on a device.** The real `ConfigurationManager` class was compiled
and driven by a transcription of `SharedPreferencesImpl`'s notification code and a ten-line
stand-in for the service's toggle path; 2,000 fresh processes per scenario. "Wrong" means the
keyboard on screen ended in a different state from the saved setting.

| Scenario | Before | After |
|---|---|---|
| One slow tap on the one-handed toggle | wrong in 1,014 / 2,000 | 0 / 2,000 |
| Switch turned on in Settings | 1,016 / 2,000 | 0 / 2,000 |
| Fast double tap (100 ms apart) | 2,000 / 2,000 | 0 / 2,000 |
| …then pressing the stop control to escape | 2,000 / 2,000 | 0 / 2,000 |
| Three slow taps (400 ms apart) | 995 / 2,000 | 0 / 2,000 |
| Slider drag, 30 writes 16 ms apart | 4 refreshes, **30** UI updates | 4 refreshes, **4** UI updates |

The ~50 % rows are the listener-order case: on a JVM the order is a coin flip per process. On a
phone the proportion will differ, and may well be stable for a given boot — which is how a defect
like this can be constant on one device and invisible on another. The 100 % rows are the
coalescing case and do not depend on order. **No device reproduction exists**: the emulator smoke
(section 7c) drives the Settings switch and reads the saved preference, not the geometry of the
keyboard on screen. The model was a throwaway and is not in the repository; the unit tests below
are what stays.

**The fix.** The service is no longer a listener on the preferences. `ConfigurationManager` is the
only one, and it calls the service through `setAfterRefreshListener(...)` strictly after the
refresh that covers each key:

- first write of a burst: refresh, then deliver — as before, minus the ordering lottery;
- later writes: the key is owed until the trailing refresh has run, then delivered;
- a new burst that supersedes a pending trailing refresh delivers what it owed;
- a key written many times in one burst is delivered once (the last row of the table: a slider
  drag used to run `setKeyboard`, the toolbar sync and the one-handed sync on every increment);
- a key written *while a refresh is running* waits for the next refresh, since the running one
  may already have read the old value;
- the consumer is guarded with `catch (Throwable)`, like the config listeners beside it.

`ConfigurationBurstCoalescingTest` pins all of it, including a source pin that the service does
not go back to registering itself. The test seam is constructor-scoped (a scheduler and a clock),
the same idiom as `ConfigPropagator`.

**Trade-off.** A write that lands inside a burst now updates the open keyboard up to 100 ms later
than it used to — but with the right value, which it previously never got.

## 3–7. CI and documentation

**3. Full-suite concurrency.** `full-test-suite.yml` had one global group, `full-test-suite`, with
`cancel-in-progress`. Runs for unrelated commits cancelled each other: PR #26's own run
(42938417424) was cancelled by the push that merged it, and any pull-request push could have
cancelled an in-flight run for `main` or the nightly. The group is now per ref.

**4. Error count.** The build's annotation step printed `head -8` of the diagnostics. It now
prints one line first — `KOTLIN ERRORS: 12 in 3 file(s) -- A.kt x7 (line …); B.kt x3 (…); …` —
then the first eight. Checked by running the step's script against a log shaped like run
42938427740's: nine annotations, inside GitHub's ten-per-step limit.

**5. Uploads.** `AGENTS.md` says every `upload-artifact` is `continue-on-error`. Three were not:
"Upload unit-test XML" and "Upload failure reports" in `build-apk.yml`, and "Upload unit-test XML"
in `full-test-suite.yml`. A full artifact quota would have turned a run that built, tested and
published into a red one.

**6. Runner image.** `emulator-smoke.yml` was already pinned to `ubuntu-24.04` with
`actions/setup-java@v5`, for a documented reason (the `ubuntu-latest` label has been migrating to
Ubuntu 26 since 2026-10-19). `build-apk.yml` and `full-test-suite.yml` now match it, which also
clears the `setup-java@v4` deprecation warning. The remaining Node 20 warnings
(`actions/checkout@v4`, `actions/upload-artifact@v4`, `gradle/actions/setup-gradle@v4`) are left:
those actions still run, and a major-version bump of each is a change with its own risks.

**7. Statements that were no longer true.**

- `AGENTS.md` said `Defaults.THEME` is `harbor`. It has been `gboard` since 2026-10-30
  (`OWNER-DECISIONS.md` was right; the short version was not).
- `AGENTS.md` said the whole suite runs "nightly, on demand, and whenever that file or
  `build.gradle` changes". It has run on every push to `main` and every pull request since
  2026-11-04.
- `README.md` and the header of `build-apk.yml` said CI runs `assembleDebug` only, not `test`.

`AGENTS.md` also gained the rule this incident is the reason for: nothing is done until the run is
green, and the report must name the run.

## 8. Nothing could check a change before the push

The dev sandbox cannot run Gradle, so `AGENTS.md` told every session that a Kotlin change is
unverified until CI says otherwise. That is true, and it was not enough: PR #26 was pushed and
merged without anyone ever having run a compiler over it.

It turns out the sandbox can run one. PyPI and `api.github.com` are on its allowlist, and they
carry a JRE, a Kotlin compiler and `android.jar`. **`scripts/ci/offline/typecheck.sh`** fetches
them once and runs the compiler's front end over a base commit and over the working tree. Without
AndroidX on the classpath a healthy tree reports about 15,000 errors, so the tool reports the
*difference*: the errors the tree has and the base does not.

- Against the commit that broke `main` it lists eleven errors that are new to the tree — every
  real one, including the two lines CI's list never reached — in under two minutes.
- It caught an error in this very change. `ConfigurationManager.kt` had been type-checked on its
  own and passed; the whole-tree run reported a redeclaration, because the new file-private
  `MainLooperScheduler` collided with one that `clipboard/ClipboardManager.kt` already declares
  in the same package. That would have been another red build.

What it cannot see, and how to read its output, is in
[`scripts/ci/offline/README.md`](../scripts/ci/offline/README.md). It is a reason to push, not a
substitute for the run.

## 9. Reported, not changed

- **Any `arena/**` branch overwrites `dev-builds`.** `build-apk.yml` publishes the rolling release
  from every branch it builds, so the "permanent" APK link is whichever branch built last, not
  necessarily `main`. That is how a session's work gets onto the owner's phone before a merge, so
  it is a deliberate convenience — but it means an unmerged experiment can replace the build of
  `main`. The release body names the branch and commit. Separating a `main`-only release from a
  per-branch one is the owner's decision.
- **Merging before CI finishes.** The workflows cannot prevent it; `AGENTS.md` now forbids it,
  which only binds a reader who follows it. Branch protection on `main` that requires the `build`
  check would enforce it. That is a repository setting, not a file in this tree.
- **The documents assume a private repository; this one is public.** `AGENTS.md`, `README.md`
  and `docs/CI-STORAGE.md` size every artifact rule against a private repository's 500 MB quota.
  Which of the two is intended is the owner's to say, so nothing was changed.
- **A two-key `apply()` costs a second `Config` refresh.** Android calls listeners once per
  changed key, so the second key of one `apply()` (the floating window's x and y, for instance)
  looks like a second write inside the burst and schedules a trailing refresh 100 ms later.
  Harmless, and not distinguishable from a genuine second write.
- **`predictionCoordinator.initialize()` runs twice in `onCreate`** — once in the manager cluster
  and again in `wireSwipeTypingComponents`. The second call is a guarded no-op, so the
  "Models loaded in N ms" log line beside it times nothing.

## Not hunted

The typing and swipe engines, the clipboard store, backup and restore, the emoji and GIF panes,
the settings screens, APK size (about 36 MB per ABI) and start-up or typing latency. One lead is
worth taking first: every preference write triggers or schedules a full `Config` refresh and a
keyboard-view reset, so anything that writes a preference while the user is typing pays that per
keystroke. Whether anything does was not checked.

## How this was verified

**By CI**, which is the compiler here. The pull request for this branch lists the run ids for
Build APK, Emulator smoke and the full unit-test suite on its head commit.

**Before the push**, in the sandbox:

- *The revert* is exact by construction: its tree hash equals that of `0e2dce4`.
- *Compilation.* `scripts/ci/offline/typecheck.sh 0e2dce4` reports nothing new for
  `src/main/kotlin`. With `--tests` it lists only `mockk`, `every`, `any` and the `io.mockk`
  imports in `ConfigurationBurstCoalescingTest.kt` — the test file's first use of MockK, a
  library the tool cannot see.
- *The new tests' logic.* All 14 tests in `ConfigurationBurstCoalescingTest` were executed
  against the real `ConfigurationManager` class, with small functional stand-ins for MockK and
  Truth, and passed. (That was before the class gained its `@Before`/`@After` pair that mocks
  `android.util.Log`, which the stand-ins did not model.) Then the fix was broken on purpose in
  fourteen ways, one at a time —
  consumer before refresh, delivery not waiting for the trailing refresh, no de-duplication,
  owed keys dropped, consumer unguarded, keys taken after the refresh, the trailing path not
  delivering, the pending refresh not cancelled, the owed set iterated in place, a wider burst
  window, the no-Looper path, and three ways of wiring the service wrongly. Every one made at
  least one test fail. Those stand-ins are not MockK: CI runs the same file against the real
  library, and that run is the one that counts.
- *The behaviour* was modelled as described in finding 2.
- *The workflow change* to the annotation step was run as a script against a log shaped like
  run 42938427740's, against a log with no compiler diagnostics, with no log at all, and with
  `python3` missing.

**Not verified at all:** anything on a real device. One-handed mode, the toolbar, the suggestion
strip and the floating window all take their live updates through the path that changed.
